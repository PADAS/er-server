# ERA-11577 — Geo-Permission support for v2 event types

## Business context

> As a conservation patrol officer with limited permissions, I need to view and
> report data using v2 event types, so that I can continue to benefit from
> EarthRanger.

**Acceptance criterion:** Geo-permissions honour the same end-user and business
contracts for events created under a v2 event type/category as they do today for
v1 — specifically, a user who holds *only* the geographic permission set for a
category can still see that category and its event types and hydrate the web
client.

Links:
- [ERA-11577](https://allenai.atlassian.net/browse/ERA-11577)
- [ERA-11554 — App crashes when user with geo-permissions to see an Event Category holding v2 event types logs in](https://allenai.atlassian.net/browse/ERA-11554)

## Root cause

The defect is **version-agnostic** and lives in the `/activity/events/categories`
list endpoint, not in any v2-specific code.

`get_event_category_queryset` filters categories using only the four *general*
permission codenames and an inline codename string:

`das/activity/views/events/categories.py:30-33`
```python
actions = ("create", "update", "read", "delete")
queryset = queryset.exclude(
    id__in=[q.id for q in queryset if not any(user.has_perm(f"activity.{q.value}_{action}") for action in actions)]
)
```

It never checks the geographic codenames (`view_{value}_gd`, `add_{value}_gd`, …).
A user holding **only** "View *X* Event Geographic Permissions" therefore matches
none of the four actions and is excluded from every category → the endpoint
returns `200 []`.

The `/eventtypes` endpoints (v1 and v2) already do this correctly via
`AllowedCategoriesMixin._build_permission_names`, which unions `ACTIONS` **and**
`GEO_ACTIONS` codenames through `make_eventcategory_permission_codename`:

`das/activity/views/events/utils.py:26-34`
```python
def _build_permission_names(self, event_category):
    action_permissions = [
        f"activity.{make_eventcategory_permission_codename(event_category, action)}" for action in ACTIONS
    ]
    geoaction_permissions = [
        f"activity.{make_eventcategory_permission_codename(event_category, action, True)}" for action in GEO_ACTIONS
    ]
    return action_permissions + geoaction_permissions
```

So two derivation paths for "can this user see this category" exist and disagree.
The categories list is the stale one.

### Why this surfaced as a "v2" problem

It isn't intrinsically v2. As part of the v2 effort the team **stopped inlining
event types in the `/categories` response** (they now come from `/eventtypes` to
avoid duplication — see ERA-11554 notes). Before that change a geo-only user got
what they needed from whatever consumed the inlined data; afterwards the client
depends on `/categories` returning the category, and it doesn't. The same
geo-only user would have been mis-filtered for v1 too; the v2 split is what made
it fatal to app hydration.

## The reported 5XX — investigated, not reproduced as a distinct bug

The ticket records Joshua's *assumption* that there are "5XX-class errors for
geo-permissions with v2 event types … likely a simple parse path issue, similar
to the CSV export fix." We traced every candidate path and **could not reproduce
a geo-permission-specific server 500**:

1. **`parse_schema` only returns `None` for empty / invalid-JSON schemas.** A
   missing `json`/`ui` key returns the parsed dict; a valid v2 event type renders
   fine. (`das/activity/schemas/eventtype_service.py:104-158`)
2. **The dedicated v2 schema endpoints handle `None` gracefully** — they return
   **207 / 422**, never 500. `SchemaResult.to_api_dict` is even annotated
   "may be None if parsing failed early."
   (`das/activity/views/types_v2.py:201-211, 259-263`)
3. **The geo permission class never parses v2 schemas.**
   `EventCategoryGeographicPermission` works off category-value codenames,
   `obj.location` and `obj.geometries` — there is no v1/v2 schema branching to
   break. (`das/activity/permissions.py:142-247`)
4. **The empty-array path returns a clean `200 []`** — the *frontend* crash on
   hydration (ERA-11554: "app crashes", "fails to hydrate") is what a non-engineer
   would describe loosely as the app "5XX-ing".

**Conclusion:** the reported 5XX is most plausibly the downstream effect of the
empty-array bug, not a separate server error. The fix below addresses it.

> **Open item — needs confirmation before we close the 5XX question.** If anyone
> has an actual server stack trace (Sentry / logs) showing a `5xx` on this
> scenario, attach it to the ticket. Absent that, we treat the 5XX as resolved by
> fixing the empty array.

### Two genuine — but separate — latent 500 risks found en route

Not part of this ticket's acceptance criteria; capture as follow-ups, fix here
only if cheap and low-risk:

- **`V2SchemaAdapter._ensure_rendered` does not guard against a `None` render.**
  `das/activity/schemas/schema_adapter.py:106` assigns `result.schema` (which can
  be `None` for an empty/invalid-JSON schema) and `get_properties` then subscripts
  it at `:115` → `TypeError` (500). This is on the **CSV/display path** for
  *malformed* schemas and is version-display-specific, not geo-specific. Low-touch
  hardening (fall back to raw schema + log) is the genuine "parse path fix"
  analogous to commit `8ebdd591c`.
- **`_get_coordinates_from_geometry` indexes unchecked.**
  `das/activity/permissions.py:217-222` does
  `geometry["features"][0]["geometry"]["coordinates"][0]` with no shape guard →
  `KeyError`/`IndexError` (500) on a POST carrying a malformed `geometry`.
  Version-agnostic.

## Proposed fix (low-touch — preferred per ticket discussion)

Make category visibility use the **single source of truth** that `/eventtypes`
already uses, instead of the stale inline check.

1. **Route the categories list through the geo-aware check.**
   In `das/activity/views/events/categories.py`, replace the inline
   `actions = (...)` exclusion in `get_event_category_queryset` with the
   `AllowedCategoriesMixin` permission-name logic (union of `ACTIONS` +
   `GEO_ACTIONS` via `make_eventcategory_permission_codename`). Either reuse the
   mixin or factor `_build_permission_names` / `_is_event_category_visible_by_user`
   into a shared helper callable from the free function. The `etag` hash
   (`etag_event_category_hash`) already derives from the same queryset, so it
   follows automatically.

2. **Make object-level detail consistent.**
   `EventCategoryObjectPermissions.has_object_permission`
   (`das/activity/permissions.py:136-139`) checks only the general codename. After
   step 1 a geo-only user will see the category in the list but still get **403**
   on `GET /categories/{id}`. Extend it to accept the geographic codename for safe
   methods, mirroring `_build_permission_names`, so list and detail agree.

3. **(Optional, low-risk) Harden `V2SchemaAdapter._ensure_rendered`** to fall back
   to the raw schema and log when `result.schema is None`, closing the latent
   display-path 500. Defer if it widens scope.

**Explicitly out of scope (follow-up tech-debt ticket):** Ernesto's suggested
rebuild of the permission classes. `EventCategoryPermissions` /
`EventCategoryGeographicPermission` do carry too many concerns (duplicated
`has_permission`, mixed object resolution + distance/geometry validation +
banning + tenant-settings access), but the list defect is gated by the *queryset*,
not those classes. Folding a rewrite into a customer-facing crash fix adds
unjustified risk.

### Files to change
- `das/activity/views/events/categories.py` — `get_event_category_queryset`
- `das/activity/permissions.py` — `EventCategoryObjectPermissions.has_object_permission`
- `das/activity/views/events/utils.py` / `utils/categories.py` — shared visibility helper (if extracted)
- `das/activity/schemas/schema_adapter.py` — optional `_ensure_rendered` guard

## Test plan (test-driven — write the failing assertion first)

New regression coverage in `das/activity/tests/test_eventcategory.py`
(none of the existing geo tests in `test_permissions.py` exercise category
listing):

1. **Geo-only user sees the category in the list.** User granted only
   `view_{value}_gd` (no general `{value}_read`) → category appears in
   `GET /categories`. Assert the *current* code fails this (empty list) before the
   fix.
2. **Version independence.** Parametrise the above over a v1 category and a v2
   category to prove the fix is not v2-special-cased and that v1 didn't regress.
3. **Detail endpoint parity.** Same geo-only user → `GET /categories/{id}`
   returns 200 (guards against the step-2 403).
4. **No over-grant.** A user with neither general nor geo permission for a
   category still does **not** see it (empty list / 403).
5. **(If step 3 of the fix is taken)** Adapter renders without raising for an
   empty/invalid-JSON v2 schema (falls back, logs) instead of 500.
